# 2026-07-29 Devlog

## 今日摘要

今天將預問診流程進一步收斂為可驗證、可重現的確定性臨床決策管線：
胸痛、頭痛與腹痛皆改用版本化固定疾病表、ClinicalFact 白名單與程式投票，
Safety 規則維持獨立且優先。同步完成醫師端規則中心、SNOMED CT 本機術語
安裝與查詢，並把 SMART on FHIR 開發沙盒接入真正的 Vue 預問診與 FastAPI
後端，讓問診、術語、規則維護、RAG 與 FHIR 授權測試形成較完整的開發閉環。

## 主訴抽取與確定性問診

- 擴充多症狀主訴抽取，所有症狀、route、finding 與時間資訊都必須附原文
  evidence，並經白名單與程式驗證後才可進入問診狀態。
- 將症狀相關事實限定在各自 route，避免把某一症狀的時間、嚴重度或警訊
  套用到另一個症狀。
- 限制只有頭痛、胸痛／胸悶與腹痛等核准主症狀可啟動對應問卷；頭暈、
  頭部外傷、視覺異常、噁心或嘔吐只能作為 finding，不能單獨誤開疼痛問卷。
- 新增逐字起始時間抽取與問卷預填；病人已明確說出「一小時前開始」時，
  可略過重複的 onset 問題，同時避免把外傷發生時間誤當成症狀起始時間。
- 支援「已持續一個月」等持續時間表達，並將模型偶爾輸出的 JSON boolean
  正規化為核准字串，避免有效抽取因格式差異整筆失敗。
- 主訴中已回答的問卷資訊會先對照實際部署的 route、field 與 option 白名單；
  單選或排他答案可直接預填，多選題的部分答案則只移除已知選項，保留其餘
  選項繼續追問。
- 語意抽取成功後以驗證結果作為 route 依據，不再讓第二次、不受相同約束的
  分類覆蓋結果。
- 新增選項層級的病人情境條件；男性病人的問卷不再顯示月經、陰道症狀、
  懷孕／產後與子宮相關手術選項，連帶移除不適用的 negated finding，
  女性、其他、不便透露或未知情境則保留原選項。

## 固定疾病表與 Safety

- 建立胸痛、頭痛與腹痛三套路由的版本化疾病表，保存來源、語料 SHA-256、
  建表模型、不能漏診標記、線索權重與審查狀態。
- 執行期只由程式計算支持票、反對票、淨票、完整度與穩定排序；LLM 不產生
  疾病候選、分數或下一題，RAG 也不參與病患端即時疾病評分。
- 三種問卷皆先執行 Safety 必問題，再依疾病表的區辨力選題；加入 70%
  完整度停止條件與 24 輪轉交上限。
- 將 Safety 觸發的鑑別方向與固定疾病表票數分開呈現，保留規則代碼、
  原始 evidence 與觸發來源，避免把安全警訊誤解為診斷排名。
- 擴充病例儲存、背景報告及醫師端載入流程，使新舊病例都能重建確定性
  評分快照與一致的臨床證據畫面。

## 醫師端規則中心

- 建立 Safety 規則管理後端，提供唯讀總覽、管理權杖驗證、版本衝突檢查、
  JSON schema 驗證、原子更新與更新前稽核快照。
- 規則微調助理只能針對已選取規則產生草稿，不能新增／刪除 rule code，
  也不能直接儲存；最終變更仍需醫師檢視、填寫理由及輸入指定確認文字。
- 規則中心可依共通、胸痛、頭痛、腹痛與結構化規則分類、搜尋及編輯。
- 後端提供語意特徵 catalog 與分類，前端以勾選器編輯
  `any_findings`／`all_findings`，並保留其他進階 JSON 條件。
- 新增更新前完成度檢查、欄位錯誤提示、成功通知及行動版版面，降低規則
  儲存失敗與誤操作的機會。

## SNOMED CT 術語整合

- 新增受授權 SNOMED CT International RF2 的本機安裝流程；RF2 ZIP、
  解壓內容與 SQLite 索引均排除於 Git，由每位部署者自行合法取得。
- installer 會驗證 RF2 Snapshot 結構、HAPI CLI 版本與 SHA-256，透過
  `CodeSystem/$upload-external-code-system` 匯入 HAPI，並等待指定概念通過
  `$validate-code` 後才完成。
- 從 RF2 Snapshot 建立唯讀 SQLite FTS 索引，供醫師端進行英文術語搜尋；
  純數字 concept ID 則由後端代理 HAPI `CodeSystem/$lookup`。
- 新增醫師端 SNOMED CT 查詢頁、分頁、錯誤處理與術語導覽連結。
- 建立固定疾病表的 SNOMED CT coding registry；疾病方向可包含多個 coding，
  新病例與既有病例載入時都會補上已驗證編碼，前端逐一顯示來源與代碼。

## SMART on FHIR 開發沙盒

- 將本機 SMART Launcher、FHIR root proxy、FastAPI 與正式 Vue build 組成
  完整 Compose stack，重用既有 HAPI FHIR R4 Server。
- Provider EHR Launch 與 standalone patient launch 完成 OAuth 後，不再停留
  在示範資料頁，而是回到真正的病患端問診。
- 前端恢復 SMART client，讀取 launch-context Patient 與
  `Patient/{id}/$everything`，沿用現有 FHIR 映射完成基本資料、病史、手術、
  用藥及過敏預填，再自動開始 AMIE 問診。
- OAuth callback 會辨識 pending launch、清除瀏覽器網址中的 authorization
  code，並顯示 Patient／Encounter context；FHIR access token 只供瀏覽器中的
  SMART client 呼叫 FHIR Server，不送入 `/chat`、RAG 或外部模型。
- Vue 與 FastAPI 改由同一 App origin 的 `/api` reverse proxy 串接；新增
  local SMART Launcher CORS gateway、`no-store` discovery response 與 Nginx
  安全 header。
- 將 `fhirclient` 2.6.3 固定於 App image 並在本機提供，不依賴外部 CDN；
  刪除舊的獨立 `index.html` 示範 reader。
- 新增 synthetic patient 入口、連線檢查、port override、持久化 consultation
  volume 與停止方式說明；此環境只供合成資料及本機開發，不可使用真實病歷。

## 開發環境

- 將 `.env` 忽略規則擴展至 repository 內所有目錄，避免前後端本機環境設定
  被誤納入版本控制；可提交的設定範本仍使用 `.env.example`。
- 新增 FastAPI runtime image，將一般 API 與 RAG 依賴拆成
  `requirements-runtime.txt`／`requirements-rag.txt`，PyTorch 使用 CPU-only
  wheel，減少不必要的 GPU runtime。
- SMART backend 掛載既有 Chroma 索引、SNOMED 資料、consultation volume
  與唯讀 Hugging Face model cache；執行期使用 offline mode 並關閉模型及
  Chroma telemetry。
- `start-smart.sh` 會先檢查 HAPI、`backend/.env`、Chroma SQLite 與 embedding
  model cache，再於啟動後驗證 `/api/health` 的 `rag_enabled` 與 collections；
  缺少必要資源時直接停止並提供 bootstrap 指令。
- 本機研究設定啟用 Gemini 醫療術語英文化與 dual-query：Gemini 只負責
  去識別化查詢正規化，本機 embedding、Chroma、RRF 與來源片段仍是檢索核心。
- 新增 root／backend Docker build context 排除規則及 `.rag-cache` 忽略項目，
  避免把環境檔、測試產物、授權術語資料與大型本機索引送入 image build。
- 新增 `future.md`，規劃後續拆分 Development／Clinical frontend、Patient／
  Clinician Shell、SMART／OIDC 身分驗證、後端 BFF session、角色授權、
  稽核與醫師確認後的 FHIR 回寫。
