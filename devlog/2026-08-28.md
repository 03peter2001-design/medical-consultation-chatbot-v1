## 國語問卷與 scenario pack adapter v0.3.0

- LLM experiment 問卷 loader 對齊 `backend/questionnaire_data` 根目錄 55 份國語 JSON，
  疾病問卷組合 `basic + history + disease`，並支援 duration、canonical 選項、條件題及
  context-sensitive 選項；`tai/` 不在可載入範圍。
- 固定順序由 orchestrator 本機強制，醫師 agent 仍取得完整剩餘問卷並選出程式指定的
  下一題；病人 agent 的 canonical answer 經本機驗證後才可驅動條件分支，無法確定分支
  時在診斷前 fail closed。
- 保留 questionnaire review status、原始 selection strategy 與 provenance；provisional
  candidate 須以 CLI 明示開啟，輸出不宣稱 clinically approved。
- 新增與 `scenario_pack_15/merged.json` 欄位相容的 adapter，將 doctor record、hidden
  patient facts、patient concerns 與 evaluator-only differential 分離，並保留 volunteered
  和 on-request 揭露規則。
- 本機參考 pack 缺少原創合成與外部模型使用核准 metadata，因此只用於唯讀 schema
  對照，沒有送至 Gemini；測試與操作範例使用全新合成 scenario pack。
- 離線驗證共 45 項測試通過；涵蓋 55 份國語問卷、條件狀態機、provisional governance、
  scenario 資訊隔離及未授權 pack 的失敗關閉。

- Orchestrator 不再 import `GeminiProvider`，兩個角色一律透過 `providers/base.py` 的
  `create_provider()` 建立 provider，保留 `JsonProvider` 作為角色層唯一依賴介面。
- Provider 優先序為 `LLM_EXPERIMENT_PROVIDER`、`LLM_PROVIDER`、Gemini key 推斷；模型
  支援 doctor/patient 角色值、實驗共用值、`GEMINI_MODEL` 與 provider 預設值。
- 預設讀取 `llm_experiments/.env` 再讀 `backend/.env`，process environment 優先；解析
  結果以 mapping 傳入 factory，不修改 process environment，也不記錄 key。
- 保留既有 `--doctor-model`、`--patient-model` 作相容覆寫，新增
  `llm_experiments/.env.example` 作為 provider-neutral 設定入口。
- 離線測試增至 32 項，涵蓋 factory 建構、環境優先序、角色模型、缺 key、不支援
  provider、secret repr 與 orchestrator runtime 組裝。
- 真實 API smoke test 已由新 base factory 讀取既有 `.env` 並成功完成合成病例 1 輪；
  未完整問卷仍正確 abstain，證明 runtime 不再依賴 orchestrator 直接建構 Gemini。

## Gemini 雙 Agent DDX 實驗 v0.1.0

- 在 `llm_experiments/` 建立合成病例限定的醫師與病人 Gemini agent；醫師只取得病歷、
  問卷與公開逐字稿，病人只取得隱藏症狀事實與目前問題，參考診斷只留在 evaluator
  邊界。
- Orchestrator 以有限狀態機限制每輪一題、題號必須來自未詢問題目，實際提問固定採
  問卷原文；完整問卷或達最大輪數後才建立暫定鑑別診斷，資料不足允許明確 abstain。
- Gemini 使用 JSON Schema 結構化輸出、停用 automatic function calling，模型輸出再由
  本機驗證 exact keys、型別、patient fact 引用與逐字稿證據，第二次無效即失敗關閉。
- 實際 `gemini-3.6-flash` smoke test 發現動態 thinking 會耗盡小型 JSON request 的輸出
  token；provider 現依 Gemini 3.x 設定 thinking level、保留 token 餘量，並只在
  `MAX_TOKENS` 時擴容重試一次。
- 僅允許 `synthetic: true` 病例，沒有把根目錄來源/授權不明的 `data/` 送往模型；新增
  全新合成偏頭痛範例。
- 離線驗證：`backend/venv/bin/python -m unittest discover -s llm_experiments/tests -v`
  共 19 項通過；`backend/venv/bin/ruff check llm_experiments` 與
  `backend/venv/bin/ruff format --check llm_experiments` 通過。
- 真實 API smoke test 使用全新合成病例與 `--max-turns 1` 通過；結果正確標記問卷不完整、
  `primary_diagnosis: null` 與 `certainty: insufficient`，未把短問診宣稱為確診。

限制：此版本不含 RAG、資料集評估器、正式 clinical Safety/triage 或產品 API 整合，
也未授權用於真實病人資料。

## SMART Launcher Patient request CORS 修正

- 本機 `127.0.0.1:8091` Launcher 的 OAuth authorize、patient selection 與 token exchange
  均成功，但 callback 對 `Patient/{id}` 只完成 OPTIONS，未送出 GET；瀏覽器顯示
  `Failed to fetch`。
- 根因是 SMART patient reader 為避免不同 launch state 取得快取病歷，使用
  `Cache-Control: no-cache`／`cache: no-store`，gateway CORS allow-list 卻未允許
  `Cache-Control`（以及瀏覽器可能伴隨的 `Pragma`）。
- Gateway 現允許這兩個 request headers，loopback origin allow-list、credential policy
  與 FHIR scope 不變；SMART sandbox/app 由 `1.1.1` 升至 `1.1.2`，`frontend-v2/` 未修改。
- 實際 OAuth round trip 通過 CORS 後另發現 HAPI `$everything` next link 的 `/fhir` base
  被 SMART public base 再附加一次，形成 `/v/r4/fhir/fhir?...` 404；FHIR root proxy 現以
  精確 `/fhir` alias 將該 pagination request 對回 HAPI base，不改變一般 resource path。
- `compose.smart.yml` 的 Backend trusted issuer 改為隨 `SMART_LAUNCHER_PORT` 產生的 public
  loopback issuer，不再使用容器內部 proxy 名稱。實際 8091 OAuth、Patient、分頁
  `$everything`、發碼與 QR 顯示完整通過，無 failed request、4xx 或 console error。
