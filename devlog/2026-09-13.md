## 醫師摘要整份確認與 FHIR 送出提示

- 開發版醫師摘要由逐欄確認改為整份病歷一次確認；任一摘要欄位為空白時不可確認，
  確認後若再次編輯任一欄位，整份病歷會回到待確認狀態。
- 完成整份確認後，「送出並儲存至 FHIR」維持可操作。若病例沒有可信的 FHIR
  Patient context，點擊後會顯示明確錯誤，不呼叫 FHIR API，也不宣稱送出成功；有
  context 時仍須經最終核對視窗才會送出。
- 這些變更只調整醫師端審閱與錯誤回饋，不改變病患問診內容、AI 草稿生成、醫師授權
  邊界或 FHIR payload contract。

## SMART STU 2.2 client 與本機 sandbox 強化

- 開發版 Provider EHR Launch 改用可設定的 SMART STU 2.2 細粒度病人讀取／搜尋
  scopes，預設只涵蓋問診預填實際消費的 FHIR resource types。瀏覽器 client 拒絕
  system scope、缺少 `launch`、沒有 patient read 權限及格式錯誤的 scope。
- OAuth authorization 明確要求 PKCE S256。Issuer 在正式模式必須使用 HTTPS，只有
  Vite development 的 loopback 可使用 HTTP；可再以 exact allowlist 限制受信任的
  FHIR issuers，並在 redirect 前拒絕含帳密、query、fragment 或未允許的值。
- SMART sandbox 的 Provider EHR 與 standalone patient launch pages 同步採用細粒度
  scopes 及 PKCE。`start-smart.sh` 修正 host HAPI 預設 port 8080／8081 不一致，驗證
  所有外部 ports；測試啟動頁現在依 runtime ports 產生連結。
- Compose 固定 proxy 的 Nginx patch tag 與 SMART Launcher 多架構 image digest，避免
  未審核的 `latest` 更新改變本機 OAuth 行為。
- 正式部署 Doctor v2 新增 `/ai-consult/launch.html`，production build 可由 UCC／EHR
  以 public client 啟動 SMART OAuth。Callback 回到原 Doctor SPA 後仍先驗證 UCC
  bootstrap，再由 `fhirclient` 完成 token exchange；若 UCC 已提供明確的 FHIR
  Patient／Encounter reference，必須與 SMART context 完全相符。
- UCC 尚未提供 FHIR 對照欄位時，Doctor 只顯示「已授權但未綁定」，不把 SMART
  Patient／Encounter 用於邀請、FHIR 寫入或任何授權判斷。既有 UCC `regSno`、CSRF、
  scope 與 encounter 驗證維持不變。Doctor multi-page build 仍輸出 `index-*.js`，保留
  eHIS deploy script 的 cache-buster 契約。
- 開發版與 v2 共用 SMART callback 完成後都會清除 URL 中的 code、state、`smart` 與
  launch-mode 暫態參數；v2 Patient 的 QR／HttpOnly session gate 不變。

## 安全與相容性邊界

- 本次維持 public browser client；access token 仍只由 `fhirclient` 用於 FHIR request，
  不會加入問診 payload 或交給 Backend。
- `openid fhirUser` 尚未預設要求，因為 Practitioner identity 尚未接入 Backend
  authorization。正式臨床身份 BFF、SMART Backend Services、UCC 與 FHIR context 的
  server-side 強制綁定、`$everything` fallback、Inferno 與院方 EHR 驗證仍屬後續工作。
- HTTP loopback、local auth bypass 與 local author fallback 仍只適用合成資料 sandbox，
  不得用於真實病人資料。
